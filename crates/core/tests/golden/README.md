# Golden-file DSP tests

Each `<fixture>.json` here pins the features `HopProcessor` (default configs, 48 kHz mono, 256-frame hops) produces from the matching `../fixtures/<fixture>.wav`, sampled every 250 ms (t = 0.25 … 2.0 s): `rms`, `peak`, the normalized `loudness`, the 64 `spectrum` bars, the 3 `bands` ratios, `flux`, `onset_age_ms`, plus the cumulative `onset_count` and exact `onset_hops` list. Values are stored at six significant figures.

The fixtures are deterministic 2.0 s clips generated by `cargo run --example gen_fixtures` (integer sample indices, one rounding step to 16-bit PCM, so the WAV bytes are byte-identical on every platform): steady sines (1 k/60/5 k Hz), a 120 BPM click train, −20 dBFS LCG noise, silence, a 50 Hz→10 kHz exponential sweep, and a gated tone burst.

`tests/golden.rs` recomputes each fixture and compares under tolerance bands: `rms`/`peak` relative 1 % (absolute floor 1e-4), `loudness` absolute 0.02, spectrum bars absolute 0.02, bands absolute 0.05, flux absolute 0.05, `onset_age_ms` absolute 6 ms (one hop), and onset hop indices exactly. The bands are wide enough to absorb the last-ULP FFT drift a pure-Rust f32 transform shows across OS/CPU, but tight enough to catch a real DSP regression (`golden_tolerances_are_tight` proves a 3× perturbation fails).

Set `SCIA_BLESS=1` when running the tests to rewrite these JSON files from the current DSP output instead of asserting. Do that only for a deliberate DSP change, and review the diff before committing. Re-run `gen_fixtures` (and re-bless) only when a fixture definition itself changes.
